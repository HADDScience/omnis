## 4. 결정된 방향 (사용자 확정)

### 4-1. 운영 규칙을 전제로 한다

> - 여러 명이 동시에 업무 지시하는 일은 없다
> - 업무 지시 시 각 업무별로 담당자를 명확히 한다

이 결정으로 **`ownerId` nullable 마이그레이션, 미배정 상태, 수령(claim) 흐름은 불필요**해졌다. 만들지 말 것.

### 4-2. 단, 문서로 가르치지 않는다 — 시스템이 행동을 유도한다

사용자 명시 요구: *"문서화해서 유저가 능동적으로 학습하는 방식이 아니라, 시스템 상에서 물 흐르듯이 따라가면서 행동을 유도하는 수동적인 유저에게서 행동을 이끌어내는 전략"*

**쓸 수 있는 도구는 셋뿐이다: 순서 · 기본값 · 잔상.**
필수 필드 + 빨간 에러, 온보딩 투어, 안내 배너는 **금지** — 벽으로 느껴져 카톡으로 회귀한다.

| 대상 | 유도 방법 |
|---|---|
| **지시** | 입력 순서를 뒤집어 **담당자를 먼저** 고르게(카톡 `@멘션`과 동일 동작). 첫 동작이 사람 선택이면 미정이 구조적으로 불가능. AI가 추론 가능한 31%(명시 9%+맥락 22%)는 미리 채워두고 확인만 하게 |
| **확인** | 알림에 `[수락]` 버튼. **수락 전까지 알림이 사라지지 않음**. 현재 알림은 사후 통보만 하고 액션 버튼이 없다(`notification-bell.tsx`) |
| **보고** | 별도 작업으로 두지 말 것. **파일을 업무에 올리는 순간** "완료로 표시할까요?" / 체크리스트 전부 체크 시 동일 질문 / 마감일 경과 시 담당자에게 반복 질의 |
| **동시 지시** | DRAFT를 **락이 아니라 신호로** 노출: "김아리님이 지금 이 프로젝트에 업무를 작성 중입니다 `[이어쓰기]` `[따로 만들기]`" |
| **위반 가시화** | 대시보드에 `확인 안 한 업무` / `3일째 진행 중` / `완료 확인 대기`. **지시자에게도 보이게** — 사회적 압력이 사람이 아닌 화면에서 나오게 |

### 4-3. AI 역할 축소

지시 입력이 구조화되면 AI는 **파싱하는 자**에서 **정리를 돕는 자**로 물러난다.
부수 효과: Gemini 호출 급감(하루 20회 한도 완화) · 즉답성 회복 · 동시성 노출 감소.

**`messages/route.ts:186`의 AI 완료 추론(`action === "complete"` → DONE + 체크리스트 전부 체크)은 삭제 대상.**
담당자가 명시적으로 완료를 누르면 추측이 사실로 바뀐다.

## 5. 남은 작업 (우선순위)

### A. 행동 유도 (핵심)
1. **지시 입력 순서 뒤집기** — `components/chat/task-cmd-modal-v2.tsx`, `task-instruction-dialog.tsx`
2. **알림에 수락 버튼** — `components/layout/notification-bell.tsx` + 알림 스키마에 액션 타입
3. **AI 완료 추론 제거** — `app/api/chat/messages/route.ts:186` (가장 작은 변경, 가장 큰 위험 감소)
4. **완료 유도** — 파일 업로드 시점 질의 (단, B-1 선행 필요)
5. **대시보드 위반 가시화** — `app/(main)/dashboard/page.tsx`

### B. 미해결 버그
1. **파일 업로드가 Vercel에서 실패** — `app/api/files/route.ts:43` 로컬 FS 기록. Vercel Blob 전환 필요. 채팅 첨부(`chat-panel.tsx:194`)와 옴니스 편집기(`section-editor.tsx:703`)가 사용
2. **고아 프로젝트** — products → projects → tasks 3단계 요청이 원자적이지 않아, tasks 실패 시 앞서 만든 프로젝트·제품이 남음
3. **낡은 드롭다운** — 모달 열 때 프로젝트 목록 스냅샷(`task-cmd-modal-v2.tsx:160`). 열어둔 동안 남이 만든 프로젝트가 안 보여 중복 생성 유발
4. **프로젝트 병합 기능 없음** — 정규화로는 `홈페이지 관리` vs `웹사이트 관리`를 못 합친다(실측: 178종 중 71%는 자동 병합 불가). 사후 병합 UI가 필요

### C. 카톡 데이터 이식
**결정된 방침: 원문 전량을 히스토리·검색용으로만 넣는다. 업무 카드로 변환하지 않는다.**
과거 데이터는 규칙이 없던 시절 것이라 담당자 미정·다중 지시·완료 불명이 그대로 딸려 온다.

- 멱등성: `ChatMessage.id`가 `String @id @default(uuid())` 이므로 **결정적 id를 직접 지정**하면 스키마 변경 없이 해결.
  키 = `sha256(방|날짜|작성자|본문|같은초내순번)` — 같은 초에 같은 사람이 `Photo`를 연달아 보내는 패턴이 실제로 있어 순번이 필수.
  `createMany({ skipDuplicates: true })`.
- ⚠️ **발신자 이름 매핑표가 필요하다.** `ChatMessage.authorId`는 User FK 필수인데 표기가 다르다:
  `김아리 박사님`→김아리 / `노혜린 하드사이언스 과장님`→노혜린 / `허채정 하드사이언스 대표님`→허채정 / `Yuhooi`→윤훈.
  로스터에 **없는 3명**: `주용석(데과21)`, `주진호`, `박소정` → 비활성 계정으로 생성 권장(삭제하면 맥락이 끊김).
  빈 작성자 84건은 앞 메시지의 연속 행이므로 병합 처리(`segment.py`가 이미 그렇게 한다).

## 6. 하지 말 것

- `ownerId` nullable 마이그레이션 / 미배정 상태 / 수령 흐름 (4-1로 불필요해짐)
- 카톡 라벨로 이식 대상을 거르기 (양쪽 시행이 합의한 비업무는 메시지의 6%뿐 — 3.4% 걸러내려고 35% 오분류 위험을 지는 건 손해)
- 대량 분류에 Gemini 사용 (하루 20회)
- 단일 LLM 패스 결과를 그대로 신뢰 (반드시 3회 다수결)
- 배포 관련 파일 수정 (`docker-compose*.yml`, `Dockerfile`, `install.synology-ssh.sh`, `docs/SYNOLOGY_*`) — 다른 세션 담당

# 카카오톡 업무 대화 이식 설계

> 대상: 2025-08-20 ~ 2026-08-21 · 9,214 메시지 · 633 세션
> 작성 2026-09-02

## 1. 목적

지난 1년의 실제 업무 대화를 옴니스로 옮긴다. 목적은 **지난 업무 이력을 업무 카드로 남기는 것**이다
(사용자 확인). 검색·주간보고·RAG의 재료가 되는 것은 부수 효과다.

## 2. 원칙

1. **원본을 왜곡하지 않는다.** 시각·작성자·담당자를 지어내지 않는다. 모르는 것은 모르는 채로 남긴다.
2. **몇 번을 돌려도 같은 결과.** 중간에 끊겨도 다시 돌리면 이어진다.
3. **이식 중 부수효과 없음.** AI 호출·알림·임베딩은 이식 경로에서 타지 않는다.
   1년 전 대화 때문에 오늘 알림이 쏟아지면 안 된다.

## 3. 범위

| 방 | 세션 | 메시지 | 이식 |
|---|---|---|---|
| 하드사이언스 인턴방 | 193 | 5,147 | ✅ |
| HADD-수원대 | 422 | 3,990 | ✅ |
| 윤훈 상무님 | 18 | 77 | ❌ **제외** |

`윤훈 상무님`은 1:1 대화다. `ChatRoom` 에는 멤버십·접근 통제가 없어서
(`roomId` 만 알면 누구나 읽는다) 넣는 순간 사적인 대화가 전 구성원에게 공개된다.
방별 접근 통제가 생기기 전까지 제외한다.

**메시지는 분류와 무관하게 전량 이식한다.** 잡담(160건)·정보공유(84건)도 함께 넣는다 —
맥락이 있어야 업무 대화가 읽힌다. 분류는 *업무 카드를 만들 대상*을 고르는 데만 쓴다.

## 4. 스키마 추가

```prisma
model ChatMessage {
  /// 원본 식별자. "kakao:<sha1(room|시각|작성자|본문)>"
  /// 이식을 여러 번 돌려도 중복이 생기지 않게 하는 유일한 장치다.
  sourceId String? @unique
}

model Task {
  sourceId String? @unique   // "kakao-session:<세션id>"
}
```

이게 없으면 "어디까지 넣었는지"를 알 방법이 없어 재실행이 곧 중복이다.

## 6. 시각 — 함정 하나

`createdAt` 은 지정할 수 있지만 **`updatedAt` 은 Prisma 가 `@updatedAt` 으로 덮어쓴다.**
대시보드가 `orderBy: { updatedAt: "desc" }` 를 쓰므로, 그대로 두면 "최근 업무" 가
1년치로 도배된다. **이식 후 raw SQL 로 `updatedAt` 을 `createdAt` 에 맞춰 교정한다.**

폴링은 안전하다 — `after` 가 "마지막으로 본 시각 이후" 만 가져오므로 과거 시각으로 삽입된
메시지는 접속 중인 사람 화면에 밀려 들어가지 않는다.

## 7. Phase A — 메시지

```
9,137 메시지 → ChatMessage
  roomId     방 2개를 ChatRoom 으로 (이름 그대로)
  authorId   위 매핑표
  content    원문 그대로
  createdAt  카톡 시각
  sourceId   kakao:<sha1>
```

`Photo`·`File` 같은 첨부 표시는 **본문 텍스트 그대로** 둔다. export 에 실물이 없어
File 레코드를 만들 수 없다. 없는 파일을 가리키는 링크를 만드는 것보다 정직하다.

되돌리기: `DELETE FROM "ChatMessage" WHERE "sourceId" LIKE 'kakao:%'`

## 8. Phase B — 업무 카드

대상은 **업무·실행가능 437세션**.

### 담당자 (다대다 도입으로 풀림)

| 상황 | 세션 | 처리 |
|---|---|---|
| 수행자 후보 1명 | 194 (44%) | 그 사람을 담당자로 |
| 후보 2명 이상 | 177 (41%) | **전원을 담당자로** |
| 후보 없음 | 66 (15%) | **담당자 없이 생성** |

후보가 여럿일 때 한 명을 고르지 않는다. "인턴들 각자 ~해주세요" 는 실제로 전원이 담당이고,
억지로 한 명을 고르면 그게 거짓이 된다.

후보가 없는 66건은 담당자 0명으로 만든다. 조인 테이블이라 표현 가능하고, 업무 상세는
이미 "미배정" 으로 그린다. **API 는 여전히 담당자 1명 이상을 요구한다** — 앞으로 들어오는
지시에는 운영 규칙(지시마다 담당자 명시)이 적용되기 때문이다. 과거에는 그 규칙이 없었다.

판정 근거는 `Task.sourceMessages` 에 남긴다.

```json
{ "source": "kakao", "sessionId": "...", "assigneeBasis": "sole-responder|multi|none",
  "messages": [{ "t": "...", "u": "...", "m": "..." }] }
```

### 상태 — 있는 그대로

- 완료 신호가 있으면 `DONE`, 없으면 `TODO`
- **`deadline` 은 원문에 명시된 경우에만 채운다.** 지연 판정이
  `deadline && deadline < now && status !== DONE` 이므로, 없던 마감일을 지어내지 않으면
  과거 미완료 업무가 지연으로 도배되지 않는다.

### 지시자

지시 메시지를 보낸 사람. 항상 특정 가능하므로 `instructorId` 는 문제없다.

### 프로젝트

이름 48종. `normalizeProjectName()` 으로 정규화해 합친 뒤 `Project` 생성.
프로젝트 없는 36건은 미지정으로 둔다.

## 9. 실행 수단 — 스크립트, 엔드포인트 아님

전용 import API 를 만들 수도 있지만 만들지 않는다.

- 실행자는 한 명(관리자)이고 로컬에서 프로덕션 자격증명으로 돌린다
- `updatedAt` 교정에 raw SQL 이 필요해 어차피 DB 직접 접근이 든다
- 엔드포인트는 공격면만 늘린다

`import-tools/` 아래 스크립트로 둔다. 먼저 로컬 스냅샷(:3000)에 돌려 눈으로 확인하고,
같은 스크립트를 프로덕션에 돌린다.

## 10. AI 사용량

Phase B 의 437세션 구조화가 유일한 AI 소비처다.
**Gemini 무료 티어는 하루 20요청이라 쓸 수 없다.** 633세션 분류 때와 같이 Claude
서브에이전트로 처리한다(선례 있음, 방식 검증됨).

임베딩 백필(`npm run db:embed`)은 이식이 끝난 뒤 별도로 돌린다. 안 돌리면 옴니스 RAG
검색에 이식 데이터가 안 걸린다.

## 11. 검증

Phase A
- 메시지 수가 원본과 일치하는가
- 두 번 돌렸을 때 늘어나지 않는가 (멱등)
- 가장 오래된/최신 메시지의 시각이 원본과 같은가
- `updatedAt` 이 `createdAt` 과 어긋나지 않는가
- 접속 중인 사용자 화면에 과거 메시지가 밀려 들어오지 않는가

Phase B
- 담당자 0명 업무가 화면에서 "미배정" 으로 보이는가
- 지연 표시가 폭증하지 않는가
- 담당자 여러 명인 업무가 각자의 "내 업무" 에 모두 잡히는가

## 12. 하지 않는 것

- 1:1 대화 이식 (접근 통제 부재)
- 없는 파일에 대한 File 레코드 생성
- 담당자 추측 (후보가 없으면 비워 둔다)
- 없던 마감일 생성
- 이식 중 알림·임베딩·AI 자동 호출

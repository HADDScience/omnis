# 채팅방을 누르면 늦게 열린다

폰에서 방을 누르면 글이 보일 때까지 1초 가까이 걸렸고, 저장본이 보인 뒤에도 글이 잠깐 사라졌다. 카톡 · 인스타 PC 만큼 빠르게 할 수 있는지 측정과 시제품으로 확인한 뒤 PR #161(머지 `65dbca7`, 2026-11-05)로 전사 · 1:1 · 단톡방에 넣었다. 업무 · 옴니스 방은 바꾸지 않았다. 동작은 [`manual/ux-rules.md`](../manual/ux-rules.md) 「기기 저장」, 코드는 `lib/room-snapshot.ts` · `components/messenger/client-room.tsx`.

## 증상

| 격리 환경에서 잰 폰(사람 방) | 중앙값 |
|---|---|
| 처음 여는 방, 탭 → 첫 글 | 854ms |
| 탭 → 진짜 입력칸 | 589ms |
| 저장본이 있는 방, 글이 보인 뒤 다시 사라진 시간 | 281ms (전사방 398ms) |

## 원인

1. **방을 옮길 때마다 서버 페이지를 왕복했다.** 방 화면은 `force-dynamic` 서버 페이지였다. 저장본 미리보기가 있어도 진짜 화면은 페이지 응답 뒤에야 왔다
2. **`ChatPanel` 이 받은 글을 버렸다.** 마운트하면서 `setMessages([])` 로 비우고 글 API 로 다시 받았다. 그래서 첫 글이 페이지 응답과 글 API 를 차례로 기다렸고, 같은 글을 두 번 읽었다. 저장본 뒤 빈 칸도 이 때문이다

## 잘못 짚기 쉬운 점

**서버 처리 약 10ms 는 격리 환경 값이다.** 방 페이지 안에서 잰 합계는 전사방 9.5ms, 사람 방 11.7ms(인증 · 권한 · 방 · 알림 설정 · 글 조회)였다. 로컬 DB 왕복이 1ms 안팎이라 나온 값이고, 운영의 Neon 왕복과 깨어나는 시간, Vercel 콜드 스타트가 빠져 있다. 이 값을 보고 서버가 충분히 빠르다고 결론 내면 안 된다.

**PC 격리 값만 보면 고칠 것이 없어 보인다.** 지연 없는 PC 는 현재 코드도 첫 글이 71~100ms 다. 차이는 지연이 있어야 드러난다.

**운영 함수 시간은 지금 읽을 수 없다.** Hobby 런타임 로그는 1시간만 남고, 요청 로그에는 시간이 없으며, `function_duration_ms` 지표는 유료 Observability Plus 를 요구한다.

**저장본이 보이는 시간은 서버가 늦을수록 길어진다.** 떠난 사이 지운 글 · 빠진 방의 글이 응답 전까지 보인다.

## 측정

조건:

- production 빌드(`next start`), 전용 Postgres DB, headless Chromium. 데모 모드 아님, service worker 막음
- 데이터: 측정 대상 전사방 · 1:1 방 각 300글, 다른 1:1 방 9개 각 40글, 스무 글에 사진 1장. 회차마다 상대가 사진 붙은 새 글 1건을 탭 직전에 쓴다
- PC: 1440×900, 지연 없음. 폰: 390×844 터치, RTT 150ms · 내려받기 1.6Mbps · 올리기 750kbps, CPU 4배 저하(CDP)
- 처음 여는 방: 회차마다 IndexedDB · localStorage 를 비운다. 저장본 있는 방: 한 번 열어 둔 뒤 잰다
- 사진 응답: NAS 가 없어 route 로 300ms 뒤 400×300 PNG 를 준다. 「글 · 첨부 완료」 의 약 300ms 는 이 가정값이다
- 회차: 조건마다 12회(서버 300ms 가정은 10회), 실패 0건

다시 재는 법: 위 조건으로 서버를 띄우고, 목록이 뜬 뒤 네트워크가 잠잠해지면 새 글을 쓰고 목록 줄을 누른다. 탭 시각은 `pointerdown` 의 `timeStamp`, 표시 시각은 `requestAnimationFrame` 마다 DOM 을 본 `performance.now()` 로 잰다. 첫 글은 `section` 안에 보이는 `[data-message-id]`, 진짜 입력칸은 `[data-composer-pill] textarea`, 완료는 새 글의 `img` 의 `naturalWidth > 0` 이다. 서버 구간은 방 페이지에 임시 기록을 넣어 재고 저장소에 남기지 않는다.

## 실험 중 찾은 버그

| 버그 | 어떻게 드러났나 | 처리 |
|---|---|---|
| **200건 한도.** 글 API 의 `changed` 는 오름차순 200건에서 잘리고 서버 시각은 앞으로 간다. 저장본 뒤로 변경이 200건을 넘으면 뒤쪽을 놓친다 | 시제품에서 떠난 사이 지운 글이 3.4초 보였다. 앞 시험이 만든 변경이 한도를 채운 탓이었다 | 첫 응답이 한도에 걸리면 이어 붙이지 않고 최신 한 페이지로 갈아 끼운다. 3초 폴링 자체의 한도는 그대로다 |
| **권한이 빠진 방의 저장본.** 현재 코드도 예전 `room:` 저장분이 로그아웃 전까지 기기에 남았다 | 빠진 방을 누른 뒤와 목록을 다시 받은 뒤 IndexedDB 키를 봤다 | 403 · 404 와 목록에서 사라진 사람 방의 저장본을 지운다. 저장본을 `snap:` 하나로 합치고 `room:` 은 페이지를 열 때 지운다 |
| **앞으로 가기 화면.** 폰에서 방 → 목록으로 돌아간 뒤 앞으로 가면 방이 아니라 새 대화 칸이 보였다. `pushState` 로 바꾼 주소라 라우터의 화면은 그대로이기 때문이다 | 운영 반영 중 e2e(`tests/feature/room-instant-open.spec.ts`) | 주소가 바뀌면 목록이 아는 전사 · 사람 방을 셸이 그린다 |

빠진 방의 글은 지금도 서버가 거절하기 전까지 잠깐 보인다. 지연 150ms 에서 A 366ms, 시제품 242ms 였다(1회).

## 돌리지 못한 조건

- 운영 서버 · Neon · 콜드 스타트. 300ms 는 가정값이다
- 실제 안드로이드, 설치한 PWA 구분, 기기에서 잰 시간
- 운영 코드로 다시 잰 A · B 비교
- 단톡방 측정(e2e 는 있다), 며칠 떠난 저장본, 40개 방 저장 용량(방당 최대 19.7KB 로 약 0.8MB 추정), 동시 사용자, 여러 탭, 오프라인
- 빠진 방 · 지운 글 · 250건 시험은 PC 에서 1회씩이다

## 운영 확인

2026-11-05 작업지시자가 iPhone 에서 「잘 된다」 고 확인했다. 확인 절차별 결과는 받지 않았다.

## 운영에서 볼 값

`/settings/ui-metrics` 의 「방 → 첫 글」 · 「방 → 첫 글(저장본)」 칸. 이벤트는 `room_first_message` · `room_first_message_saved` 이고 값은 ms 숫자뿐이다. 목록에서 전사 · 사람 방을 누른 경우만 쌓이고 주소로 바로 연 방은 재지 않는다. 이 배포 전의 값이 없어 배포끼리만 비교한다. 실사용자가 적어 표본이 작다.

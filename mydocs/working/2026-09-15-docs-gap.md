# 2026-09-15 — 한 것과 `mydocs` 에 적힌 것의 차이

2026-09-09 이후 `origin/main` 에 커밋 74건, PR #6~#19 가 들어왔다. 그중 #18·#19 는
다른 세션이 돌린 문서 스윕이다. **그 스윕이 덮지 못한 자리**를 찾아 적는다.

여기 적은 것은 전부 명령으로 확인한 것이다. **Omnis 쪽은 고치지 않았다** — 어느
것을 어떤 순서로 메울지는 사람이 정할 일이라서다. 홈페이지에서 나온 한 건만
그 자리에서 고쳤다(맨 아래). 틀린 함정 항목이라 두면 다음 사람이 그걸 믿는다.

## 어떻게 비교했나


## A. 규약에서 벗어난 것

### A-1. `orders/20260915.md` 의 frontmatter 가 네 칸이 아니다

```yaml
# 20260909.md · 20260914.md          # 20260915.md
kind: snapshot                        status: working      ← 허용값 밖
status: active                        owner: 정우창         ← 규약에 없는 칸
canonical: AGENTS.md                  updated: 2026-09-15
last_verified: 2026-09-09             scope: 채팅 · 업무 스레드 …
```

`status` 의 허용값은 `active` `historical` `superseded` 다. `working` 은 없는 값이고,
`kind` · `canonical` · `last_verified` 세 칸이 빠졌다. 같은 폴더의 앞 날짜 파일들은
모두 네 칸을 지킨다.

### A-2. `plans/2026-09-10-company-records.md` 가 `status: draft`

역시 허용값 밖이다.

### A-3. canonical 문서 다섯 건이 내용은 바뀌었는데 `last_verified` 가 그대로

| 문서 | last_verified | 마지막 수정 | 무엇이 바뀌었나 |

## B. 작업은 있는데 기록이 없는 것

### B-1. 실측 출력이 남지 않은 PR 다섯

품질 게이트는 "돌린 명령과 그 출력을 붙인다"이고, 그 자리는 `working/` 이다.

## 메우는 순서 (제안)

싼 것부터. 1~2 는 기계적이고, 3~4 는 판단이 든다.

1. **frontmatter 두 건** (A-1 · A-2) — 값만 맞추면 된다
2. **`last_verified` 다섯 건** (A-3) — 내용을 실제로 확인한 뒤 날짜를 올린다
3. **계획서 archives 이동** (A-4) — 어느 것이 끝났는지는 사람이 판단한다
4. **`tech/crm.md` 신설** (B-2) — 가장 크고 가장 오래 비어 있다
5. **품질 게이트 표에 `narrow-audit` 한 줄** (B-3)
6. **PR #8 · #12 · #13 · #15 · #16 의 실측** (B-1) — 지난 실행 출력이 남아 있지
   않으면 다시 돌려야 한다. 비용 대비 가치를 먼저 따져야 하는 항목이다

**두 저장소 모두에서 틀린 문장이다.** 2026-09-10 에 홈페이지 `AGENTS.md` 와 Omnis
`AGENTS.md` 의 배포 절은 고쳤는데 이 함정 목록을 빠뜨렸다. 함정 목록은 다음 사람이
"이건 이미 겪은 문제"라고 믿고 읽는 자리라, 규약만 고치고 여기를 두면 소용이 없다.

옛 문장은 지우지 않고 취소선으로 남겼다 — 2026-09-08 이전 기록을 읽을 때 그때는
사실이었다는 것이 보여야 한다(규칙 2).

같이 `mydocs/README.md` 의 `last_verified` 를 09-07 → 09-15 로 올렸다. 목록과 실제
파일이 맞는지 확인한 뒤에 올렸다(tech 1 · troubleshootings 1 · working 1, 어긋남 없음).

나머지는 깨끗하다 — frontmatter 네 칸을 전부 지키고, 계획서 2건은 이미 `archives/`
로 가 있다. `working/` 스냅샷의 날짜 어긋남은 정상 범위다.

# 카톡 동기화 — 폴더에 있는 방을 전부 옮긴다

사용자 지시: 앞으로 지정한 카톡 폴더에 있는 방은 무조건 다 옮긴다. 방 이름은 사전 등록하지 않는다.

## 결정

- 폴더 이름은 `import-config.json` 의 `syncFolder` 에 둔다. 저장소가 공개라 코드에 넣지 않는다.
- 폴더를 잘못 읽으면 사적인 방까지 운영에 들어간다. 탭을 못 찾거나, 목록이 비었거나, 방이 너무 많거나, 아는 방이 없거나, 새 방이 너무 많으면 한 방도 건드리지 않고 멈춘다.
- 처음 보는 방은 전부 참여자 전용이고 분류 · 카드를 켜지 않는다. 참여자는 CSV 발화자 + 나.
- 1:1 은 방 이름이 상대 표시명이고, 발화자가 나와 그 사람뿐이며, 상대 계정이 있을 때만이다. 틀리면 단톡방 글이 1:1 에 섞이므로 애매하면 단톡방으로 둔다.
- 이름 없는 단체방은 CSV 이름이 모두 같아 섞인다. 목록 이름을 방 키로 쓰고, 이미 있는 방은 `listName` 으로 잇는다.
- 방 열기는 행 더블클릭이다. 선택 + Return 은 열리지 않는 방이 있었다.
- `auto` 없는 방은 설정을 바꾸지 않는다. 제외 줄 · 권한 규칙은 그대로다.
- `state.json` 의 `importedCsv` 가 동기화마다 지워져 같은 CSV 건너뛰기가 듣지 않던 것을 고쳤다.

## 범위 밖

자동 실행, 파일 탭 실물 받기, 과거 사진 받기.

## 검증

- `pnpm run typecheck` 통과 · `pnpm run lint` 오류 0 · `pnpm run test:unit` 통과 · `python3 -m unittest import-tools/test_kakao_folder.py` 통과
- `--from-csv` 건식(운영 읽기만): 지금 설정 11개 방 모두 넣을 글 0. 수동 등록 방을 뺀 설정에서는 새 방 9개가 수동 설정과 같은 종류 · 참여자로 등록됐다.
- **실제 카톡 조작은 이 코드로 돌리지 않았다.** 폴더 탭 · 더블클릭은 별도 스크립트로 같은 동작을 확인했다. 첫 실행은 `--dry` 로 본다.

## 첫 실제 실행 (2026-11-04)

- `--dry` 첫 실행이 「방 750개」 안전장치에 걸려 멈췄다. 탭은 찾아 눌렀지만 목록은 전체 탭 그대로였고, 방은 열지 않았다.
- 바로 이어 같은 클릭을 한 번 더 한 진단에서는 0.1초 안에 751행 → 12행으로 바뀌었고, 방 11개가 설정과 일치했다. 실패는 재현되지 않았다.
- 첫 클릭이 듣지 않은 이유는 확정하지 못했다. 카톡이 뒤에 있을 때 클릭이 창을 앞으로 가져오는 데만 쓰였을 가능성이 있다.
- 그래서 원인과 관계없이 전환을 확인하게 고쳤다. 카톡이 앞으로 나온 것을 확인하고, 전체 탭(행이 많다) → 폴더 탭(행이 적다) 순서로 눌러 행 수로 확인하며, 안 바뀌면 다시 누른다. 세 번까지 안 바뀌면 멈춘다. 접근성으로는 선택된 탭을 알 수 없어(`AXSelected` 가 모두 거짓) 전체 탭을 거친다.
- 시험에서 빠졌던 까닭: 폴더 읽기는 AppKit · 실제 창이 필요해 PR #141 시험이 판단 함수만 돌렸다. 전환 판단을 `switch_to_folder` 로 빼 시험에 넣었다.
- 고친 뒤 건식이 「폴더 탭을 찾지 못했다」로 멈췄다. 메인 창이 친구 탭(979행)이라 폴더 탭 줄이 없었다. 채팅 목록 화면이 아니면 채팅 버튼을 눌러 먼저 돌아가게 했다. 첫 실패의 원인도 이것일 수 있다.
- 탭 줄이 옆으로 밀리면 전체 탭이 목록에서 빠지거나 좌표가 영역 밖이 된다. 탭 줄을 굴려 영역 안에 들어온 탭만 누른다.
- 카톡이 26.9.0 으로 올라간 뒤(2026-11-03 15:38) 방 창의 접근성 id 가 `_NS:441` → `_NS:443` 으로 바뀌어, 창이 열렸는데 못 찾았다. id 대신 Send 버튼이 있는 창으로 찾는다. 창을 못 찾은 방 7개의 창이 열린 채 남아 접근성 동작으로 닫았다.
- 저장 창의 Save 를 막 뜬 직후 누르면 `-25204` 가 난다. 이 오류는 잠시 다시 누른다.
- 방이 연달아 2개 실패하면 나머지 방을 열지 않고 멈춘다.
- 수정본 실측: `--dry` 는 11개 방 모두 받기 성공, 방별 넣을 글이 CSV 집계와 일치했다(DB 접속 일시 실패 1개 방은 `--from-csv` 로 다시 확인). 뒤이은 `--target prod` 는 실패 방 0 으로 끝났다.
- `--dry` 뒤 `--target prod` 는 카톡에서 CSV 를 다시 받으므로, 그 사이에 온 글은 건식 없이 들어간다. 이번에는 9건이 그랬고, 모두 건식 CSV 마지막 시각 뒤의 글이었다.

## 빈 방 건너뛰기와 소요 시간 (2026-11-04)

오늘 운영 실행은 23분이었다. 새 글 0건인 8개 방이 616초(방마다 71~86초)를 썼다.

**왜 돌았나:** 같은 CSV 건너뛰기는 이미 있었지만, 8개 방은 처음이라 완료 기록이 없었다. CSV 는 내보낼 때마다 같다(어제 · 오늘 파일 4개 방 해시 일치). 그래서 이 수정이 없어도 다음 실행부터 건너뛴다.

**고친 것:** 건너뛰면 놓치는 경우를 막았다. 기존 코드는 `kakao.ts` 가 정상 종료하면 완료로 적었는데, 분류 · 카드 라운드 · 사진 설명 · 사진 색인 실패는 종료 코드 0 으로 끝난다. 그 뒤 CSV 가 안 바뀌면 재시도되지 않는다.

- `kakao.ts` 가 남은 일을 보고하고, 남은 일이 있으면 완료 기록을 지운다. 보고가 없어도 끝나지 않은 것으로 본다.
- 건식 · `--no-import` 로 받아 둔 사진은 `mediaPending` 으로 표시해 다음 실행에서 넣는다.
- 방 설정 · 제외 목록이 바뀌면 다시 돌린다.
- 건식도 같은 조건으로 건너뛴다. 전 방 점검은 `--from-csv` 로 한다.
- 단계별 `⏱`, 방별 `카톡 N초` · `이식 N초` 를 남긴다.

**가장 오래 걸린 방 531초 내역** (`prod.log` 에는 시작 · 끝만 있어, 데이터 파일 수정 시각과 운영 DB 시각을 읽어 나눴다. 경계는 근사다)

| 단계 | 초 | 근거 |
|---|---|---|
| 수집 · 분류 | 11 | `final.json` |
| 메시지 62건 | 45 | `round52` 입력 파일 |
| 구조화 — Claude + 카드 10개 적용 | 115 | `round52` 출력 파일, 첫 첨부 시각 |
| 첨부 38장 93MB | 56 | `File.createdAt` |
| 사진 설명 37장 (동시 3) | 206 | `File.describedAt` |
| 임베딩 — 업무 · 글 · 사진 | 98 | `EmbeddingChunk.updatedAt` |

임베딩에서 새 업무 카드 색인까지 48초가 걸렸다. 업무 84건이 실행마다 해시 비교 대상으로 다시 뽑히기 때문이다(새로 10 · 그대로 84). 빈 방의 실제 실행(약 75초)이 건식(약 25초)보다 긴 차이와 크기가 맞지만, 운영에서 단계별로 재지는 않았다.

**병렬화는 하지 않는다.** 건너뛰기 뒤 남는 것은 새 글이 있는 방뿐이고, 오늘 기준 3개 방 760초다. 동시에 돌려도 상한은 가장 긴 방(529초)이라 많아야 231초 줄고, 카드 구조화를 한 방씩 돌리면 더 준다. 그 대가로 공유 파일 5개와 `structure/drafts.json` · 라운드 번호의 동시 쓰기를 고쳐야 한다. 가장 긴 사진 설명은 이미 동시 3 이다.

**시험:** 로컬 DB 복제본(`omnis_kakao_fast`)과 임시 데이터 폴더. `import_rooms` 를 실제로 돌려 12개 시나리오를 확인했고, 11개 방 `--from-csv` 건식이 넣을 글 0 · 실패 0 이었다. 시나리오는 Claude · Gemini 호출을 막으려 `--no-structure --no-embed` 로 돌렸다. 실패 보고는 `leftover` 값을 주입해 확인했고, 실제로 Claude · 사진 설명이 실패한 경우는 돌리지 않았다. 운영 · 카톡에서는 이 코드를 돌리지 않았다.

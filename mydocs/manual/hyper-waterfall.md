# Hyper-Waterfall — 이 저장소가 AI 와 일하는 방식

> 원 출처: [edwardkim/rhwp 의 `hyper_waterfall.md`](https://github.com/edwardkim/rhwp/blob/main/mydocs/manual/hyper_waterfall.md).
> 논지는 그대로 가져오고, Rust · CLI 전제와 rhwp 고유 도구(`replay --capsule` 영수증,
> `cargo clippy` 게이트 사슬)는 걷어냈다. 실행 규약은 [`AGENTS.md`](../../AGENTS.md) 가 정본이다.

## 1. 왜 필요한가

**워터폴**은 철학이 옳았다 — 계획하고, 문서화하고, 검증하라. 느린 게 문제였다.
계획서 2주, 구현 4주. 시장이 기다려주지 않았다.

**애자일**은 속도를 얻었지만 대가가 있었다. 문서가 사라지고("코드가 곧 문서"),
스프린트마다 방향이 흔들리고, 기술 부채가 "나중에"로 밀리고, 지식이 사람 머리에 갇혔다.

**바이브 코딩**은 더 극단으로 갔다. AI 가 준 코드를 읽지 않고 수락한다.
겉보기에는 빠르지만 **이해하지 못한 코드는 고칠 수도 없다.**

```
규율 (문서·계획·검증) ←──── 트레이드오프 ────→ 속도
      워터폴 ◄──────────────────────────────► 애자일 / 바이브 코딩
```

둘 다 가질 수는 없었다 — AI 가 없던 시대에는.

## 2. 정의

**거시적으로는 워터폴, 미시적으로는 애자일.**

```
거시 (타스크 수준) — 워터폴의 규율:
  계획 ──→ 구현 ──→ 검증 ──→ 마감
   │       │       │       │
   ▼       ▼       ▼       ▼
  문서    커밋    실측출력  보고서

미시 (단계 안, 수십 분) — 애자일의 속도:
  구현 → 검증 → 피드백 → 수정 → 검증 → …
   AI    자동화   사람판단   AI    자동화
```

전통 워터폴이 느렸던 이유는 **사람이 전부 했기 때문**이다. 계획서 2일, 코드 1주,
테스트 3일, 문서 2일. Hyper-Waterfall 에서는 AI 가 쓰고 사람이 검토한다.
**규율은 그대로, 속도만 다르다.**

| | 애자일 | Hyper-Waterfall |
|---|---|---|
| 계획 | 백로그 카드 한 줄 | 수행 계획서 (`mydocs/plans/`) |
| 문서 | 선택 | 필수 — AI 가 쓴다 |
| 리뷰 | 코드 리뷰 (선택) | 계획 승인 + 결과 검증 (필수) |
| 속도 | 2주 스프린트 | 수 시간 사이클 |
| 지식 | 사람 머리 | `mydocs/` |

## 3. 세 원칙

[`AGENTS.md`](../../AGENTS.md) 의 "세 원칙" 절이 정본이다. 요약하면:

1. **구현 목표가 AI 컨텍스트에 유지되게 한다** — 결정은 문서로 외부화한다
2. **통제권은 작업지시자가 유지한다** — 계획은 AI 가, 승인은 사람이
3. **컨텍스트 유지를 주기적으로 확인한다** — 잊기 시작하면 경고 신호

셋 다 "사람은 절대 생각을 멈추지 않는다"의 구체적 실천이다.

## 4. 왜 AI 가 있어야 가능한가

**문서화 비용이 사라진다.** 개발자가 워터폴에서 가장 싫어한 것이 문서 작성이었다.
AI 가 쓰면 사람은 검토만 한다. `mydocs/` 의 문서 중 사람이 직접 쓸 것은
`feedback/` 뿐이다.

**지식이 외부화된다.** 애자일의 가장 큰 리스크는 버스 팩터다. 핵심 개발자가
떠나면 프로젝트가 멈춘다 — 지식이 머리에만 있으니까. 여기서는 모든 결정과
디버깅 과정이 파일에 남는다.

**단, 낡은 문서는 없는 문서보다 나쁘다.** 그래서 `mydocs/` 의 모든 문서가
`status` 와 `last_verified` 를 스스로 선언한다 — [`mydocs/README.md`](../README.md).

## 5. 이 저장소에 적용할 때의 조건

이 방법론은 아무 데나 쓸 수 있는 게 아니다. 필요 조건:

1. **도메인 전문성** — AI 에게 방향을 제시하려면 도메인을 알아야 한다
2. **아키텍처 판단력** — AI 의 설계 제안을 평가할 수 있어야 한다
3. **품질 기준** — "이 정도면 충분하다"를 판단할 수 있어야 한다
4. **규율** — 편하다고 바이브 코딩으로 빠지지 않는 자기 통제

부적합한 경우: 도메인을 모르는 채 AI 에 의존할 때, "빨리 만들고 버릴" 프로토타입,
AI 출력을 검증할 능력이 없을 때.

## 6. rhwp 에서 가져오지 않은 것

| rhwp 요소 | 여기서 뺀 이유 |
|---|---|
| `rhwp replay --capsule` 작업 영수증 | rhwp CLI 고유 기능. Omnis 에 대응물이 없다 |
| `lineage` · `audit` 재현율 회계 | 위와 같음 |
| `cargo clippy` 3단 게이트 사슬 | Rust 전용. `npm run verify` 로 대체 |
| GitHub Issue 자동 채번 · 마일스톤 | 이 저장소는 Issue 를 쓰지 않는다. 필요해지면 그때 |
| 시각 회귀 (`render-diff`) | 문서 렌더링 엔진이 아니다. Playwright E2E 로 대체 |
| 도구별 규칙 파일 8종 (`.clinerules` 등) | Claude Code 단일 도구. 늘어나면 그때 포인터로 |

빼놓은 것을 나중에 넣을 때는 **필요가 생긴 뒤에** 넣는다. 쓰지 않을 절차를 미리
세우면 규율이 아니라 의식(儀式)이 된다.

## 7. 결론

> AI 는 배율기다. 프로세스가 없으면 빠른 혼돈을, 좋은 프로세스가 있으면 비범한
> 결과를 만든다.

애자일이 속도를 위해 포기한 것 — 문서 · 계획 · 체계적 검증 — 을 AI 의 힘으로 되찾는다.
워터폴이 규율을 위해 포기한 것 — 속도 — 도 AI 의 힘으로 되찾는다.

# 2026-10-06 — WeKnora 방식 이식 실험 (Agentic · 정확성 · 비용/속도)

작업지시자 결정 (2026-10-06):

- **범위**: WeKnora 기법을 `bench/` 에 하나씩 이식해 효과를 따로 잰다. 로컬 Docker 로 띄운 실제 WeKnora 를 기준점으로 함께 잰다.
- **첨부 파싱**: 2단계로 넣는다. 검색·에이전트 비교가 끝난 뒤, 로컬 DB 에만 색인한다.
- **체감 평가**: 블라인드 A/B 화면에서 한다.
- **비용 상한**: 약 5만 원 (작업지시자 개인 부담).

## 왜

Tencent WeKnora(커밋 `bccb4b1`, 2026-09-30)와 코드 수준으로 비교했다 (2026-10-06 대화). Omnis 지식 쪽에 비어 있는 것은 다섯 가지다.

1. 첨부 문서 색인
2. 키워드 점수 — 지금은 `ILIKE` 로 포함 여부만 본다
3. 가중 융합과 리랭크
4. 질의 재작성
5. 다단계 에이전트 — 지금은 도구를 최대 5회 부른다

이것들이 실제로 무엇을 얼마나 바꾸는지는 아직 재 본 적이 없다.

지금 기준선은 `results-261002` 의 `native`(gemini-3.8-flash@low) 다. 16문항에서 심판 평균 1.75/2, 질문당 16.4원, p50 3.7초였다.
**문항이 쉬워 천장에 닿아 있다.** 이 문항들로는 기법 간 차이가 드러나지 않는다. 그래서 먼저 어려운 문항을 만든다.

## 가설

| | 가설 | 반증 조건 |
|---|---|---|
| H1 | pg_trgm 점수 + 가중 RRF 를 쓰면 고유명사·코드·숫자 문항의 검색 Recall@8 이 오른다 | Recall@8 차이가 3회 반복 범위 안 |
| H2 | 리랭크와 질의 재작성은 정확도를 올리지만 비용·지연도 늘린다. 둘을 저울질할 값을 얻는다 | 심판 점수 변화가 없거나 원가가 2배를 넘음 |
| H3 | ReAct 20회 + WeKnora 식 도구(grep·read_document)를 주면 다단계 문항 성공률이 오른다 | 다단계 문항의 만점률 차이가 반복 범위 안 |
| H4 | 실물 WeKnora 는 범용 문서 RAG 라서 업무 DB 질문(상태·담당자·마감)에서 Omnis 보다 못하고, 첨부 문항에서는 낫다 | 반대 결과 |

## 비교할 팔(arm)

모든 팔은 같은 생성 모델(`gemini-3.8-flash@low`), 같은 임베딩(`gemini-embedding-001` 768차원), 같은 로컬 스냅샷 DB 를 쓴다. 다른 조건은 하나씩만 바꾼다.

| 팔 | 무엇 | WeKnora 근거 |
|---|---|---|
| **N0** `native` | 현행 프로덕션 `askOmnisRoute` 그대로. 기준선 | — |
| R0 `hybrid` | 현행 검색 + 단발 생성 (ILIKE, 동일 가중 RRF k=60, top-8) | — |
| R1 `wk-kw` | R0 + 키워드를 **pg_trgm 유사도 점수**로, RRF 를 **벡터 0.7 / 키워드 0.3** 가중으로 | `retrieval_config.go:92-101`, BM25 대체 |
| R2 `wk-query` | R1 + **질의 이해**(재작성·의도 분류, flash-lite) + recall 이 낮을 때만 질의 확장 | `query_understand.go`, `query_expansion.go` |
| R3 `wk-rerank` | R2 + 상위 30을 **LLM 리랭크**(flash-lite) + MMR 다양화 → top-8 | `knowledgebase_search_rerank.go`, `reranking/mmr.go` |
| R4 `wk-parent` | R3 + 걸린 청크의 **부모 확장** (카드 전체, 업무 전체, 앞뒤 메시지) | parent-child 청킹 |
| **A1** `wk-agent` | ReAct **최대 20회**. 검색은 R-best 를 쓴다. 도구는 `search_knowledge`·`grep_chunks`(정확 일치)·`read_document`(원문 전체)·`list_documents` + 기존 Omnis 읽기 도구 + `todo_write`. 도구 결과는 토큰 예산 안에서 자르고, 컨텍스트가 길어지면 압축한다 | `agent/engine.go`, `tools/definitions.go`, `compaction/` |
| **WK** `weknora-real` | 로컬 Docker WeKnora v0.8.2. 같은 말뭉치를 Markdown 문서로 넣고 API 로 호출한다. 빠른 Q&A(RAG)와 에이전트 두 모드 다 | 실물 |
| D (2단계) | 첨부 텍스트를 추출해 로컬 DB 에 색인한 뒤 N0·A1 에 붙인다 | docreader |

R-best 는 2단계의 검색 지표만으로 고른다. 생성 비용 없이 정할 수 있다.

## 테스트 케이스 — 질문 세트 v4

`~/work/omnis-import/eval/agentic-261006.json` 에 둔다. 저장소 밖이다. 사내 업무 내용이 들어가기 때문이다.

| 유형 | 수 | 예시 형태 | 주로 재는 것 |
|---|--:|---|---|
| 회귀 (기존 3세트) | 36 | 기존 문항 그대로 | 퇴보가 없는지 |
| 다단계 (multi-hop) | 8 | "X 업무 담당자가 같은 주에 맡은 다른 업무는?" | Agentic |
| 집계·목록 | 6 | "이번 달 마감인데 아직 안 끝난 견적 관련 업무 몇 개?" | Agentic, 정확성 |
| 바뀐 결정 (stale 함정) | 4 | 기존 `changed-decisions` 형식 | 정확성 |
| 정확 문자열 | 6 | 사건번호·제품코드·금액·사람 이름 | 키워드 검색 (H1) |
| 답 없음 | 4 | DB 에 없는 사실을 묻는다. "모른다"가 정답 | 환각 |
| 모호 | 2 | 대상이 둘 이상이다. 되묻거나 가정을 밝히면 정답 | Agentic |

- **문항마다 정답 근거를 단다.** 형식은 `expect`(기대 문자열), `gold`(근거 `EmbeddingChunk` 의 source·sourceId 목록), `minSteps`(최소로 필요한 도구 단계 수)다.
- **작성 절차**: AI 가 로컬 스냅샷에서 후보 문항과 근거를 뽑아 초안을 만든다. **정답 확정은 작업지시자가 한다.** 정답을 AI 가 정하면 AI 에게 유리한 시험이 된다.

## 지표

| 목표 | 정량 | 정성 (A/B 화면) |
|---|---|---|
| **1. Agentic** | 다단계·집계·모호 문항의 만점률. 평균 도구 호출 수와 종류. 첫 검색이 빗나간 뒤 질의를 바꿔 다시 찾은 비율. 반복 한도에 닿은 비율. 심판의 **과정 점수** 0~2 (필요한 근거를 다 찾아 연결했는가). `judge.ts` 를 확장한다 | "알아서 해냈다" 1~5 |
| **2. 질의 정확성** | 심판 0~2 평균·만점률·환각 수. 근거 적중률. stale 함정에 걸린 수. 답 없음 문항을 맞게 거절한 비율. **검색만** 따로: Recall@8 · MRR · NDCG@10 (`gold` 기준, WeKnora 평가 지표와 같다) | 답 만족 1~5, 근거를 믿을 수 있는가 1~5 |
| **3. 비용·속도** | 질문당 원(심판 제외), 입출력 토큰, 호출 수, p50·p90, 단계별 ms, 월 추정(하루 50건) | 기다릴 만했나 1~5 |

- 각 팔을 **3회 반복**해서 평균과 범위를 적는다. 범위가 겹치면 "차이 없음"으로 판정한다.
- 심판은 기본 gemini-2.5-pro 다. Gemini 계열끼리 편향이 있을 수 있어서, 주요 팔 1회분은 **claude-sonnet-5 로 교차 채점**한다 (`ANTHROPIC_API_KEY` 있음).

## 블라인드 A/B 화면 (정성)

- **위치**: `/lab/ab`. `NODE_ENV=development` 이고 ADMIN 일 때만 열린다. 그 밖에는 404 다.
  **로컬에서 `next dev` 로만 띄운다.** `next start` 는 운영 DB 에 붙는다.
- **흐름**:
  1. 질문 세트에서 뽑거나 직접 질문을 입력한다.
  2. 두 팔을 동시에 실행한다.
  3. 답을 무작위로 A·B 에 배치한다. 각 쪽의 도구 호출 단계를 실시간으로 보여준다.
  4. 평가자가 선호(A / B / 비슷)와 항목별 1~5점, 메모를 남긴다.
- **기록**: `bench/results/lab-ab/votes.jsonl` 에 남긴다. git 에는 넣지 않는다.
  평가가 다 끝난 뒤 `bench/report-ab.ts` 로 어느 쪽이 어느 팔이었는지 공개하고 집계한다.
- **비교 쌍**: N0 vs A1 (주), N0 vs R-best, A1 vs WK.
- **소요 시간**: 블라인드를 위해 두 답을 동시에 띄운다. 소요 시간은 각 답 아래에 숫자로 따로 보여준다. 체감 속도는 "기다릴 만했나" 점수로 따로 받는다.

## 단계

각 단계가 끝나면 커밋하고, 결과는 `mydocs/working/2026-10-06-weknora-lab.md` 에 실측 출력과 함께 붙인다.

1. **질문 세트 v4 와 측정 기반**
   - 후보 문항과 근거 초안을 만든다 → **작업지시자가 정답을 확정한다**.
   - `bench/retrieval-eval.ts` 를 만든다 (Recall@8·MRR·NDCG@10, 생성 없음).
   - 실행기에 누적 원가 상한 `BENCH_BUDGET_KRW` 를 넣는다. 넘으면 멈춘다.
2. **검색 이식 R1~R4**
   - 로컬 DB 에만 `pg_trgm` 확장을 켠다. 운영은 건드리지 않는다.
   - 검색 지표로 R0~R4 를 비교하고 R-best 를 고른다.
   - 생성까지 하는 정량 평가는 R0 와 R-best 만 3회 돌린다.
3. **에이전트 이식 A1**
   - `bench/agent/` 에 ReAct 루프, 도구, 압축을 만든다.
   - 심판에 과정 점수를 추가한다.
   - N0 vs A1 을 3회 돌린다.
4. **실물 WeKnora**
   - 스크래치 폴더의 클론을 `docker compose` 로 띄운다. 외부로 나가는 통신은 whitelist-only 모드로 막는다.
   - 말뭉치 내보내기 스크립트(카드·업무·채팅 → Markdown)와 API 어댑터를 만든다.
   - WK 2모드를 3회 돌린다.
5. **A/B 화면과 체감 평가**
   - `/lab/ab` 를 만든다 → 작업지시자가 평가한다 → 블라인드를 풀고 집계한다.
6. **(2단계) 첨부 색인**
   - 로컬 전용 표 `lab_file_chunks` 를 raw SQL 로 만든다. **Prisma 스키마는 바꾸지 않는다.**
   - 추출 방식: PDF·이미지는 Gemini 파일 입력, hwpx·docx 는 XML 파싱. 구형 HWP 는 건수만 보고한다.
   - 첨부 문항으로 N0 · A1+D · WK 를 비교한다.
   - **최종 보고**: 무엇을 운영에 넣을지 권고한다. 실제 적용은 별도 계획서로 진행한다.

## 위험

| 위험 | 대응 |
|---|---|
| 로컬 스냅샷이 낡았다 | 1단계 시작 시 `db:snapshot` 날짜를 보고서에 적는다. 모든 팔이 같은 스냅샷을 쓴다 |
| 실물 WeKnora 의 자원(ParadeDB·Redis·docreader·프론트) | 기본 profile 만 띄운다. 메모리를 보고 판단한다. 안 뜨면 Lite 단일 바이너리로 간다 |
| 사내 데이터가 WeKnora 로 들어간다 | 로컬 Docker 볼륨에만 둔다. outbound 는 whitelist-only 로 막는다. 실험이 끝나면 `docker compose down -v` 로 지운다 |
| 블라인드가 깨진다 (말투·길이·속도로 팔을 짐작) | 두 팔의 답 형식 지시를 똑같이 준다. 평가자가 팔을 짐작했다고 메모하면 그 표는 따로 집계한다 |
| 정답을 AI 가 정한다 | 정답 확정은 작업지시자가 한다 (단계 1) |

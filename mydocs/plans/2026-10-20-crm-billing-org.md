# CRM 기관의 청구처 — 견적 받는 곳과 세금계산서 받는 곳을 잇는다

상태: 2026-10-20 작업지시자 승인(「계획서에 반영하고 진행해줘」). 빈값 처리는 아래 「기존 데이터의 빈값」. 스키마 추가와 운영 마이그레이션이 들어가 AGENTS.md 타스크 사이클 2단계(승인)를 거친다.

## 왜

대학은 견적을 학과·연구실이 받고, 세금계산서는 산학협력단 앞으로 나간다. 두 곳은 서로 다른 기관이다.
`lib/crm-invoice-match.ts` 는 세금계산서를 **같은 기관의 견적**에만 잇는다. 그래서 학과 견적에는 계산서가 붙지 않는다.
지금은 견적 상세(`app/(main)/crm/quotes/[quoteId]/page.tsx`)가 합계가 같은 계산서를 후보로 내밀고, 사람이 손으로 잇는다.

세금계산서 연동 개선안의 2단계다. 1단계는 홈택스 수집, 3단계는 견적에서 바로 발행하는 기능이다.
3단계에서 「이 견적의 계산서는 어느 사업자번호 앞으로 나가는가」를 물을 때 이 값이 답이 된다.

### 로컬 스냅샷 실측 (2026-10-20)

| 항목 | 값 |
|---|---|
| 매출 세금계산서 | 32장. 견적 연결 12 · 기관 연결 32 |
| 산학협력단 앞 계산서 | 10장. 견적 연결 3 |
| 학과로 갈라진 실제 사례 | `가천대 의과대학`(견적 1, 사업자번호 없음) ↔ `가천대학교 산학협력단`(계산서 3) |
| 대학 본체와 산학협력단이 한 기관 | 울산대학교 · 성균관대학교 — 계산서가 이미 대학 기관에 이어진다. 갈라 둘 필요 없음 |

지금 데이터에서 효과를 보는 곳은 가천대 1건이다. 산학협력단 앞 계산서 10장 중 7장이 견적과 이어지지 않았지만, 대부분은 CRM에 해당 견적이 없어서다. 이 작업으로 늘어나는 연결은 많지 않다.
그래도 하는 이유는 3단계(견적에서 발행) 때문이다. 학과 견적에서 계산서를 발행하려면 청구처가 정해져 있어야 한다.

## 무엇을 만드나

### 1. 스키마 — `CrmOrg.billingOrgId` (자기 참조)

```prisma
model CrmOrg {
  // …
  /// 세금계산서를 받는 기관. 비어 있으면 자기 자신이다.
  /// 대학 학과 → 산학협력단처럼 견적 받는 곳과 계산서 받는 곳이 다를 때만 채운다.
  billingOrgId String?
  billingOrg   CrmOrg?  @relation("BillingOrg", fields: [billingOrgId], references: [id], onDelete: SetNull)
  billedOrgs   CrmOrg[] @relation("BillingOrg")
}
```

- 청구처의 사업자번호·상호는 **청구처 기관 자신의 칸**(`bizRegNo`, `name`)을 쓴다. 복사하지 않는다.
- 별도의 「청구처」 표를 두지 않는다. 산학협력단은 이미 기관으로 들어와 있고(계산서 이식이 만든다), 기관이 아닌 청구처는 아직 없다.
- 한 단계만 허용한다. 청구처의 청구처는 막는다. 자기 자신을 가리키는 것도 막는다.
- 대표자명과 계산서 받을 이메일은 3단계 발행에 필요할 때 넣는다. 지금 넣으면 쓰는 곳이 없다.

#### 기존 데이터의 빈값 — NULL 은 「청구처 = 자기 자신」

- 마이그레이션은 NULL 허용 칸 추가뿐이다(기본값 없음). 기존 줄을 다시 쓰지 않는다.
- 읽는 쪽은 전부 `billingOrg ?? org` 로 읽는다. NULL 인 기관은 지금과 같이 동작한다.
- 백필은 아는 쌍(가천대) 1건만. 계산서 이식 · 견적 즉석 생성 등 새로 생기는 기관도 NULL 로 들어간다.
- 자기 자신으로 채우지 않는다. 의미 없는 값이 모든 기관에 생기고, 기관을 만드는 경로마다 채워야 하며
  하나라도 빠지면 NULL 과 자기 참조가 섞인다. 자기 참조 금지 규칙과도 부딪힌다.
- 검증: 청구처를 하나도 채우지 않은 상태에서 매출 계산서 전부의 잇기 결과가 **바꾸기 전 코드와 같은지** 비교한다.
  가천대 쌍을 채운 뒤에는 그 쌍만 달라지는지 본다.

### 2. 입력 — 기관 상세 화면

- `app/(main)/crm/orgs/[orgId]/page.tsx` 에 「세금계산서 받는 곳」 줄을 추가한다. 다른 기관을 고르거나 비운다.
- 청구처가 정해진 기관이면 「이 기관 앞 견적의 계산서를 받는 곳」 목록(`billedOrgs`)을 보여 준다.
- PATCH `app/api/crm/orgs/[orgId]` 의 Zod 스키마(`orgCreateSchema`)에 `billingOrgId` 를 추가한다. 서버에서 자기 자신과 두 단계 연결을 거부한다.

### 3. 잇기 — 세금계산서 ↔ 견적

- `loadOrgsForMatching` 이 각 기관의 견적에 **이 기관을 청구처로 둔 기관의 견적**을 합친다.
  산학협력단 앞 계산서가 들어오면 학과 견적까지 후보가 된다.
- 계산서의 `orgId` 는 지금처럼 산학협력단으로 둔다. `quoteId` 만 학과 견적을 가리킨다. 기관별 매출은 「누구에게 청구했나」 기준으로 남는다.
- 견적 상세의 후보 찾기(orphans)는 청구처가 있으면 청구처 앞 계산서를 먼저 찾는다.

### 4. 백필

`scripts/backfill-billing-org.ts` — 알려진 쌍만 채운다. 이름으로 찾고, 없으면 건너뛴다. `--apply` 없이는 바꿀 것만 찍는다.

| 견적 받는 기관 | 청구처 |
|---|---|
| 가천대 의과대학 | 가천대학교 산학협력단 |

채운 뒤 `가천대 의과대학` 견적과 `가천대학교 산학협력단` 계산서를 다시 잇는 것은 견적 상세의 기존 「연결」 버튼으로 사람이 한다. 스크립트가 잇지 않는다.

## 단계

1. 스키마 · 마이그레이션 · Zod → verify: `prisma migrate dev` 로컬 적용, `pnpm run verify`
2. 기관 화면 입력 + API 검증 → verify: 자기 자신 · 두 단계 연결이 400 으로 거부되는 시험, 320px narrow-audit
3. 잇기 로직 → verify: `crm-invoice-match` 단위 시험 — 산학협력단 계산서가 학과 견적에 이어지는 경우, **청구처가 없으면 이어지지 않는 경우**
4. 백필 스크립트 → verify: 로컬 dry-run 출력
5. 보고서 `mydocs/working/2026-10-20-crm-billing-org.md`, `mydocs/tech/crm.md` 흐름도에 청구처를 추가

## 운영 반영 (승인 따로)

`pnpm run db:deploy`(운영 Neon) → 백필 `--apply` → main 머지. 순서는 AGENTS.md 「마이그레이션 먼저, 머지 나중」.

## 하지 않는 것

- 세금계산서 발행(3단계), 홈택스 수집(1단계)
- 대학 외 사례를 찾아 자동으로 청구처를 추정하는 것 — 이름 유사도로 맞추면 「대구경북과학기술원부설한국뇌연구원」 같은 오답이 난다(crm-invoice-match 주석)

# 채팅 · 업무 · 일정 푸시와 켜고 끄기

작업지시자(정우창) 결정을 옮겨 적고, 받는 사람 규칙 · 스키마 · 단계를 정한다.
앞 작업: [`2026-09-22-web-push.md`](2026-09-22-web-push.md)(VAPID · 구독 · `createNotification` 이 푸시도 보낸다).
결과와 실측: [`../working/2026-10-29-push-notifications.md`](../working/2026-10-29-push-notifications.md).

## 지금 상태

- 푸시는 `createNotification` 하나로만 나간다 — 벨 행(`Notification`)을 만들면 같은 내용이 기기로도 간다
- 종류는 chat_mention · task_* · column_review · website_inquiry · crm_invoice_request. **채팅 일반 글과 일정에는 푸시가 없다**
- 끄는 길은 「이 기기 구독 해제」 하나뿐이다. 종류별 · 방별로 끌 수 없다

## 작업지시자 결정 (2026-10-29)

1. **채팅 푸시 — 모든 방, 모든 글, 기본 켜짐.** 전사방 · 업무방 · 사람 1:1 · 단톡방
   - 방별로 끈다: 방 목록 꾹 누르기 메뉴 · 왼쪽→오른쪽 밀기 칸 · 방 머리줄에 「알림 끄기 / 켜기」. 방 키 단위 `ChatRoomPref.muted`
   - 내가 쓴 글 · 시스템 계정 글에는 보내지 않는다
   - **벨 행을 만들지 않고 푸시만** 보낸다(방 목록의 안읽음 배지가 따로 있다). 멘션은 지금처럼 벨에도 남긴다
   - **그 방을 보고 있으면 띄우지 않는다** — service worker 가 포커스된 창의 주소를 본다. 방마다 tag 를 줘 쌓이지 않고 바뀌게(renotify)
   - 누르면 그 방이 열린다. 본문은 보낸 사람 · 방 이름 · 앞 몇십 자
2. **옴니스 답 푸시 — 그 방을 보고 있지 않을 때만.** 답이 끝났을 때, 확인 카드가 떴을 때(「확인이 필요해요」). 방별 끄기를 따른다
3. **일정 — 내가 볼 수 있는 캘린더(audience)에 새 일정이 들어오면, 동기화 때.**
   처음 들여오는 기존 일정에는 보내지 않는다. 바뀐 · 취소된 일정은 범위 밖. 반복 일정은 마스터 하나. 벨에도 남긴다(`calendar_event_added`), 누르면 캘린더의 그 날짜
4. **업무 — 담당자로 새로 지정되면.** 모든 지정 경로를 점검한다. 자기 지정 제외, 같은 사람에게 중복 없음
5. **설정(마이 = /settings)에 채팅 · 업무 · 일정 알림 켜고 끄기.** 끄면 그 종류의 **푸시만** 멈추고 벨 기록은 남는다.
   같은 화면에 이 기기의 구독 상태와 「이 기기에서 알림 받기」, iOS 는 홈 화면 앱에서만 된다는 안내

## 받는 사람 규칙

정본은 순수 함수 `lib/notify-rules.ts` 다. 시험이 같은 파일 옆(`notify-rules.test.ts`)에 있다.

### 채팅 글 — 방 종류별 후보

| 방 | 후보 |
|---|---|
| 전사방 (`room:<id>`, 업무 연결 없이 쓴 글) | 로그인할 수 있는 구성원 전원(`isActive`) |
| 업무방 (`task:<id>`, 업무 스레드에 쓴 글) | **담당자 전원 · 지시자** + **그 업무방에 글을 쓴 적 있는 사람**(지우지 않은 글) + **그 업무방을 즐겨찾기한 사람** |
| 사람 1:1 · 단톡방 | 참여자 |
| 옴니스 1:1 | 방 주인 한 명(옴니스 답 · 확인 카드) |

업무방의 「그 외」 두 무리를 넣은 이유 — 업무방은 표가 없는 가상 방이라 참여자 명단이 없다. 담당 · 지시만 받으면
스레드에 의견을 남긴 사람(검토자 · 동료)이 답을 모른다. **글을 쓴 것**과 **즐겨찾기**는 사람이 이미 한 행동이라
새 설정 없이 「이 방을 따라간다」 는 뜻으로 읽을 수 있다. 업무 탭에서 그 업무를 열어 본 것만으로는 넣지 않는다(기록이 없다).

전사방에서 `#슬러그` 로 업무에 이은 글은 **쓴 자리(전사방)** 를 따른다 — 전사방 사람들이 읽은 글이다.
업무 스레드(업무방 · 업무 상세 · 오른쪽 패널의 업무 탭)에서 쓴 글이 업무방 글이다.

### 후보에서 빼는 사람 (순서대로)

1. 글쓴이
2. 시스템 계정(🤖 · 옴니스) — 그리고 **시스템 계정이 쓴 글은 아무에게도 보내지 않는다**(재구성 알림 · 완료 확인 대기 줄). 옴니스 1:1 의 답은 별도 경로(결정 2)
3. 그 방을 끈 사람(`ChatRoomPref.muted`, 방 키 단위)
4. 채팅 알림을 끈 사람(`NotificationPref.chatPush = false`)
5. 같은 글로 멘션 알림(chat_mention, 벨 + 푸시)을 받는 사람 — 같은 글로 두 번 울리지 않게

멘션 푸시는 방을 꺼도 간다(나를 부른 글이다). 채팅 알림 전체를 끄면 멘션 푸시도 멈춘다(벨에는 남는다).

### 채팅 푸시를 내지 않는 글

- `/업무` · MCP `create_task` 가 함께 올리는 지시 원문과 업무 카드 — 담당자는 같은 순간 `task_assigned` 를 받는다
- 고친 글 · 지운 글

### 업무 지정

`assignmentTargets(previous, next, actor)` — 다음 담당자에서 중복을 걷고, 이미 담당이던 사람 · 지정한 사람 자신 · 시스템 계정을 뺀다.
모든 경로가 이 함수를 지난다:

| 경로 | 코드 |
|---|---|
| 화면 업무 생성 · 채팅 `/업무` · AI 초안 확인 | `POST /api/tasks` |
| 화면 업무 수정(담당자 바꾸기) | `PATCH /api/tasks/[taskId]` → `updateTask` |
| MCP `create_task` · 에이전트 확인 카드 `create_task` | `runTool("create_task")` (에이전트는 `executeWrite` → `runTool`) |
| MCP `update_task` · 에이전트 확인 카드 `update_task` | `runTool("update_task")` → `updateTask` |
| `#슬러그` 재구성 | 담당자를 바꾸지 않는다(`TaskRebuildResult` 에 담당자 칸이 없다) — 지정이 일어나지 않는다 |

### 일정

- 대상 캘린더의 `audience` 가 ALL 이면 구성원 전원, ADMIN 이면 관리자(`role = ADMIN`)만
- 그 일정의 주최자(ORGANIZER 메일)가 옴니스 사용자면 그 사람은 뺀다 — 자기가 만든 일정이다
- **그 캘린더를 처음 동기화하는 주기(`syncedAt` 이 비어 있음)에는 보내지 않는다.** 공개 범위를 넓힐 때는
  일정 행이 새로 생기지 않으므로 저절로 보내지 않는다(새로 생긴 행만 센다)
- 새로 생긴 행 중 마스터(`recurrenceId = ""`)만, 취소(`CANCELLED`)와 이미 끝난 일정은 뺀다
- 한 캘린더에서 한 번에 4건 이상 들어오면 한 건씩이 아니라 「새 일정 N건」 하나로 묶는다

### 설정 — 무엇을 끄면 무엇이 멈추나

| 설정 | 멈추는 푸시 | 벨 |
|---|---|---|
| 채팅 알림 | 채팅 글 · 옴니스 답 · 확인 카드 · chat_mention | 멘션은 남는다(채팅 글은 원래 벨이 없다) |
| 업무 알림 | `task_*` 전부(지정 · 완료 확인 · 재구성 · 상태 변경 · 수락) | 남는다 |
| 일정 알림 | `calendar_event_added` | 남는다 |
| (없음) | column_review · website_inquiry · crm_invoice_request 는 늘 간다 | — |

끈 것은 **푸시만** 멈춘다 — 벨 기록은 남겨 놓치지 않게 한다. 방별 끄기도 같다(채팅 글은 원래 벨이 없다).

## 스키마 (추가만)

```prisma
model ChatRoomPref {
  …
  /// 이 방의 채팅 푸시를 끈다(2026-10-29). 멘션 푸시와 벨은 그대로
  muted Boolean @default(false)
}

/// 사람마다 종류별 푸시 켜고 끄기. 행이 없으면 전부 켜짐
model NotificationPref {
  userId       String   @id
  chatPush     Boolean  @default(true)
  taskPush     Boolean  @default(true)
  calendarPush Boolean  @default(true)
  updatedAt    DateTime @updatedAt
}
```

마이그레이션 `20261029050000_push_prefs` — 칸 하나 · 표 하나를 더할 뿐이다. 기본값이 곧 결정(전부 켜짐)이라 백필은 없다.
**로컬 DB(5433)에만 적용한다.** 운영 migrate 는 머지 전에 작업지시자가 한다.

## 보내는 방식

- 푸시는 응답 뒤에 보낸다 — `after()`(Next) 로 넘기고, 요청 밖(스크립트 · Workflow 단계)이면 그 자리에서 기다리지 않고 돌린다.
  실패는 로그만 남기고 글쓰기 · 업무 저장 · 동기화를 막지 않는다
- 받는 사람이 많아도(전사방 ~12명) **질의는 사람 수와 상관없이 고정**: 후보 · 끈 방 · 설정 · 구독을 한 번씩 읽고 발송만 병렬로 한다
- 페이로드에 `roomPath`(그 방 주소)를 싣고, service worker 가 포커스된 창이 같은 주소면 띄우지 않는다
- 발송 기록: `PUSH_LOG_FILE` 이 있으면 누구에게 무엇을 보냈는지 한 줄씩 남기고, `PUSH_DRY_RUN=1` 이면 푸시 서비스에 보내지 않는다.
  로컬 DB 는 운영 스냅샷이라 실제 구독이 들어 있다 — dev 와 검증은 dry run 으로 띄운다

## 단계

1. 스키마 · 마이그레이션 · 순수 규칙(`lib/notify-rules.ts`) + 단위 시험
2. 발송 배관 — `lib/push.ts`(종류 설정 · 여러 사람 · 발송 기록 · dry run) · `lib/notifications.ts`(종류별 설정) · service worker(보는 방 · renotify)
3. 채팅 · 옴니스 답 푸시 — `lib/chat-push.ts`, 전사방 · 업무방 · 사람 방 · 에이전트에서 부른다. 방별 끄기 API · 목록 · 머리줄
4. 업무 지정 경로 정리 · 일정 알림(동기화) · 캘린더 `?day=` · 하루 한 번 크론에 캘린더 동기화(그동안 크론은 캘린더를 당기지 않았다)
5. 설정 화면 — 종류별 켜고 끄기 · 기기 구독 상태 · iOS 안내
6. 검증 — verify · test:unit · 발송 기록 검증 스크립트 · 스크린샷 · 로컬 e2e(omnis_test)

# 채팅 품질 — 실시간 전송을 빼고 먼저 고칠 것

작업지시자(정우창) 2026-10-30: 옴니스가 채팅 중심 서비스가 됐으니 채팅 품질을 올린다.
실시간 통로(Pusher · Ably 등)는 뒤로 미루고 **그 밖의 것부터** 한다.

실시간 통로를 붙여도 기준은 DB 와 커서다(끊겼다 붙으면 커서로 따라잡는다). 그래서 아래 1·2 는
실시간을 붙이기 전에 고쳐 둬야 하는 토대이기도 하다.

## 이미 있는 것 (다시 만들지 않는다)

| 기능 | 위치 |
|---|---|
| 보내는 즉시 임시 말풍선(`temp-…`) | `components/chat/chat-panel.tsx` handleSend |
| 위로 무한 스크롤 + 보던 자리 유지 | `loadOlder` · `message-list.tsx` anchorRef |
| 검색 결과로 가기(around · at) — 시각이 같으면 id 로 가름 | `app/api/chat/messages/route.ts` GET |
| 방별 안 읽음 수 | `lib/chat-rooms.ts` · `ChatRoomPref.lastReadAt` |

## 코드에서 찾은 문제

### 1. 폴링 · 이전 페이지 커서가 시각만 본다 — 글이 빠진다

`GET /api/chat/messages` 의 `after` 는 `createdAt > after`, `before` 는 `createdAt < before`, 정렬은 `createdAt` 하나다.

- **같은 시각의 글이 페이지 경계에 걸리면 빠진다.** 카톡 이식분은 초 단위라 같은 시각이 흔하다(around 쪽 주석에 이미 적혀 있다).
  이전 페이지를 넘길 때 경계 시각의 나머지 글이 영영 안 보인다
- **늦게 커밋된 글이 빠진다.** `createdAt` 은 INSERT 시점 값이다. A(12:00:00.100)가 커밋되기 전에 B(12:00:00.200)가 먼저 커밋되고
  폴링이 B 를 읽으면 커서가 .200 으로 가서 A 는 다시 안 온다. 업무 재구성처럼 트랜잭션이 긴 글에서 날 수 있다

**고침**: 커서를 `(createdAt, id)` 쌍으로 바꾸고 정렬도 `[createdAt, id]` 로. 폴링은 커서보다 **몇 초 앞부터** 다시 읽고
id 로 중복을 거른다(늦은 커밋 대비). 스키마 변경 없음.

### 2. 남이 고치거나 지운 글이 내 화면에 안 바뀐다

폴링은 새 글만 가져온다. 내 수정 · 삭제는 `applyMessageChange` 가 그 자리에서 갈아 끼우지만,
**남이 고친 글은 새로고침 전까지 옛 내용 그대로**다. 지운 글의 본문이 남의 화면에 계속 보인다 — 삭제의 뜻이 없어진다.

**고침**: 폴링 응답에 「커서 이후 고쳐지거나 지워진 글」을 함께 싣고, 화면은 id 로 갈아 끼운다.

→ **결정 A** 필요(아래).

### 3. 전송이 실패하면 말풍선이 「보내는 중」 으로 영원히 남는다

- 서버가 오류를 돌려주면 `reportIncident` 만 하고 임시 말풍선은 그대로 둔다(주석: 「화면 동작은 그대로 두고」). 다시 보낼 방법이 없다
- **네트워크가 끊겨 `fetch` 가 던지면** 그 아래 `pausePolling.current = false` 에 닿지 않는다 → **그 방의 폴링이 멈춘 채로 남는다.**
  새 글이 안 들어오는데 화면은 멀쩡해 보인다

**고침**: try/finally 로 폴링 재개를 보장. 실패한 말풍선은 「전송 실패 · 다시 보내기 · 지우기」 로 바꾼다(카톡 · 슬랙과 같은 모양).

→ 다시 보내기에서 **같은 글이 두 번 저장될 수 있다**(요청은 서버에 닿았는데 응답만 끊긴 경우). **결정 B** 필요.

### 4. 위로 올려 읽는 중에 남의 글이 오면 맨 아래로 끌려 내려간다

`message-list.tsx` 는 새 글이 붙으면 무조건 `scrollTo(bottom)` 이다. 옛 대화를 읽다가 남이 한 줄 쓰면 읽던 자리를 잃는다.

**고침**: 맨 아래 근처(약 120px)에 있거나 **내가 보낸 글**이면 따라 내려간다. 아니면 자리를 지키고
아래에 「새 메시지 N개 ↓」 알약을 띄운다. 누르면 내려가고 사라진다.

## 결정할 것

> 2026-10-30 작업지시자 결정: **A1 · B1**. `changedAt` · `clientId` 를 한 마이그레이션으로 넣는다.

**A. 남의 수정 · 삭제를 어떻게 알아낼까**

| 안 | 내용 | 비용 |
|---|---|---|
| A1 (추천) | `ChatMessage.changedAt DateTime?` 열 + `@@index([roomId, changedAt])`. 고치기 · 지우기 때 함께 찍는다. 폴링은 `changedAt > 마지막 확인 시각` 만 본다 | 마이그레이션 1개(운영 DB 먼저 적용). 백필 불필요(null = 바뀐 적 없음) |
| A2 | 스키마 그대로. `roomId` 로 걸러 `editedAt` · `deletedAt` 을 본다 | 인턴방은 1만 줄이 넘는다. 3초마다 방 전체를 훑어 **Neon 컴퓨트가 늘어난다** |
| A3 | 이번에는 하지 않는다 | 지운 글 본문이 남의 화면에 남는다 |

**B. 다시 보내기의 중복을 막을까**

| 안 | 내용 |
|---|---|
| B1 (추천) | `ChatMessage.clientId String? @unique`. 화면이 보낼 때 만든 id 를 싣고, 같은 id 로 다시 오면 서버가 처음 글을 돌려준다. A1 과 같은 마이그레이션에 넣는다 |
| B2 | 스키마 그대로. 드물게 같은 글이 두 번 남는 것을 감수한다 |

## 단계

1. **커서** — API 의 after/before 를 `(createdAt, id)` 쌍으로, 폴링 겹쳐 읽기. 경계 시각이 같은 글 · 늦은 커밋을 재현하는 시험을 먼저 쓴다
2. **전송 실패** — finally 로 폴링 재개, 실패 말풍선 · 다시 보내기 · 지우기. (B1 이면) clientId 마이그레이션 + 서버 중복 처리
3. **남의 수정 · 삭제** — (A1 이면) changedAt 마이그레이션, 폴링 응답에 changed 목록, 화면 갈아 끼우기
4. **스크롤** — 따라 내려갈지 판정, 「새 메시지 N개 ↓」 알약
5. **검증** — `pnpm run verify` · `pnpm run test:e2e` · ux-rules 11~30 · narrow-audit. 결과는 `mydocs/working/2026-10-30-chat-quality.md`

단계마다 커밋한다. 작업은 브랜치 워크트리(`feat/chat-quality`)에서 한다.
마이그레이션이 들어가면 **운영 DB 적용은 머지 전에 따로 승인받는다.**

## 범위 밖

- 입력 중 표시 · 접속 상태 — 실시간 통로가 있어야 의미가 있다
